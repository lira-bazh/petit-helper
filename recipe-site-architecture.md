# Помощник Petit Planet — архитектура сайта и базы данных

## 1. Общая идея

Название сайта: **«Помощник Petit Planet»**.

В публичной части есть только два основных раздела:

1. **Рецепты**
2. **Цветы**

**«Предложить рецепт»** — действие внутри раздела «Рецепты», а не отдельный основной раздел навигации.

Административная часть с модерацией рецептов остаётся отдельной служебной страницей и не показывается в основном меню.

Система пользователей не нужна.

Для хранения данных можно использовать **MongoDB Atlas** на бесплатном тарифе.

Основные коллекции:

- `recipes`
- `ingredients`
- `recipe_submissions`
- `flowers`
- `flower_crosses`

При необходимости позже можно добавить:

- `effects`
- `settings`
- `moderation_log`
- `flower_images`

---

# 2. Раздел «Рецепты»

На главной странице выводятся карточки рецептов без крупных изображений.

Карточка содержит:

- название рецепта;
- силу;
- эффект;
- ингредиенты;
- количество ингредиентов;
- необходимое качество ингредиента.

Пример:

```text
Ароматное фруктово-злаковое молоко

Сила: 60
Эффект: Повышение выносливости

Фрукт (фиолетовое качество) ×1
Пшеница ×1
Молоко ×1
```

На странице доступны:

- поиск по названию;
- поиск по ингредиентам;
- фильтр по эффекту;
- фильтр по силе;
- фильтр по ингредиентам;
- фильтр по качеству ингредиентов.

Отдельная страница «Подробнее» не нужна — весь рецепт отображается непосредственно в карточке.

---

# 3. Форма «Предложить рецепт»

Пользователь может предложить новый рецепт без регистрации.

Поля формы:

- название рецепта;
- сила;
- эффект;
- список ингредиентов;
- количество каждого ингредиента;
- требуемое качество;
- дополнительный комментарий.

После отправки рецепт **не появляется сразу в основной базе**.

Он создаётся в коллекции:

```text
recipe_submissions
```

со статусом:

```text
pending
```

---

# 4. Страница модерации

Страница доступна только администратору.

Отдельная система пользователей для этого не обязательна. Доступ можно защитить:

- паролем;
- серверной сессией;
- Basic Auth;
- секретным admin-token.

На странице отображаются предложения со статусами:

```text
pending
approved
rejected
```

Модератор может:

- посмотреть предложенный рецепт;
- изменить данные перед публикацией;
- одобрить рецепт;
- отклонить рецепт;

После одобрения данные переносятся в коллекцию `recipes`.

---

# 5. Раздел «Цветы»

Это отдельный раздел сайта, но в том же проекте и в той же базе данных.

Цель страницы — показывать комбинации скрещивания для каждого вида цветка.

На странице **«Цветы»** лучше показать **все таблицы сразу на одной странице**, потому что их немного.

Для каждого цветка отображается компактная **диагональная таблица**:

- по горизонтали — цвет второго родителя;
- по вертикали — цвет первого родителя;
- в ячейке — цвет результата;
- нижняя половина матрицы может быть пустой или приглушённой, потому что таблица симметрична.

На одной странице можно вывести блоки для:

- Подсолнуха
- Розы
- Амариллиса
- Георгина
- Протеи
- Лилии
- Агапантуса
- Маргаритки
- Канн
- Портулака
- Колокольчика
- Фиалок

Источник данных — пользовательская таблица **«Цветы»**. В макетах и базе нужно опираться именно на неё.

Пример логики одного блока:

```text
Маргаритка

             Белый    Жёлтый    Бирюзовый
Белый          —      Шампань        ?
Жёлтый         ·         —           ?
Бирюзовый      ·         ·           —
```

Для удобства можно оставить только лёгкие инструменты:

- поиск по названию цветка;
- переключатель «показывать только известные комбинации»;
- краткую легенду символов и цветов.

Отдельный экран для каждого вида цветка не нужен. Все таблицы идут сеткой на одной странице. На мобильном экране карточки располагаются по одной, а сама маленькая матрица остаётся целиком внутри карточки.

# 8. ingredients

Отдельный справочник ингредиентов нужен обязательно, потому что одни и те же ингредиенты повторяются во многих рецептах.

Пример:

```js
{
  _id: ObjectId,

  name: "Клубника",

  slug: "strawberry",

  categories: [
    "fruit",
    "red-fruit"
  ],

  color: "red"
}
```

Другой пример:

```js
{
  _id: ObjectId,

  name: "Лобстер",

  slug: "lobster",

  categories: [
    "seafood"
  ]
}
```

---

# 9. Категории ингредиентов

В рецептах встречаются не только конкретные ингредиенты, но и условия:

- фрукт;
- овощ;
- зерновые;
- морепродукт;
- пресноводная рыба;
- красный фрукт;
- жёлтый фрукт;
- зелёный фрукт.

Поэтому ингредиенты должны иметь категории.

Например:

```text
Клубника
→ fruit
→ red-fruit
```

```text
Манго
→ fruit
→ yellow-fruit
```

```text
Лобстер
→ seafood
```

Это позволит рецепту содержать требование:

```text
любой фрукт
```

а не конкретно клубнику или манго.

# 11. flowers

Справочник видов цветов.

```js
{
  _id: ObjectId,
  name: "Daisy",
  slug: "daisy"

```

Примеры:

- `lily`
- `daisy`
- `sunflower`
- `mooncycle-rose`
- `amaryllis`
- `bellflower`
- `king-protea`

```js
{
  _id: ObjectId,
  slug: "daisy",
  names: {
```

# 12. flower_crosses

Коллекция комбинаций скрещивания.

```js
{
  _id: ObjectId,

  flowerId: ObjectId("..."),

  parent1: {
    color: "Yellow",
    rarity: 0
  },

  parent2: {
    color: "White",
    rarity: 0
  },

  result: {
    color: "Champagne",
    rarity: 1
  },

  source: "Petit Planet - Flower breeding"
}
```

Более компактный вариант для MVP:

```js
{
  flowerSlug: "daisy",
  parent1Color: "Yellow",
  parent1Rarity: 0,
  parent2Color: "White",
  parent2Rarity: 0,
  resultColor: "Champagne",
  resultRarity: 1
}
```

# 13. Что хранить у цветов

На старте можно не создавать отдельную коллекцию цветов-оттенков.

Достаточно хранить значения строками:

- `White`
- `Yellow`
- `Teal`
- `Champagne`
- `Lime`
- `Purple`
- `Cream`
- `Tangerine`
- `Pastel Pink`
- `Black Velvet`

Если позже понадобится:

- единый перевод цветов;
- сортировка по группам;
- собственные цветовые swatch-иконки;
- фильтрация по редкости,

можно добавить справочник `flower_colors`.

---

# 14. Статусы предложений

Используются три статуса:

```text
pending
approved
rejected
```

### pending

Рецепт ожидает проверки.

### approved

Рецепт одобрен и добавлен в `recipes`.

### rejected

Рецепт отклонён.

---

# 15. Одобрение рецепта

При нажатии «Одобрить»:

1. сервер получает документ из `recipe_submissions`;
2. проверяет ингредиенты;
3. создаёт новый документ в `recipes`;
4. меняет статус предложения на:

```text
approved
```

5. записывает дату модерации.

Пример:

```js
{
  status: "approved",
  reviewedAt: ISODate()
}
```

---

# 16. Отклонение рецепта

При отклонении:

```js
{
  status: "rejected",

  moderatorComment: "Такой рецепт уже существует.",

  reviewedAt: ISODate()
}
```

Удалять предложения необязательно — их можно оставить для истории.

---

# 17. Повторяющиеся ингредиенты

Если рецепт требует:

```text
gриб + гриб
```

не нужно создавать две одинаковые записи.

Лучше хранить:

```js
{
  ingredientId: ObjectId("..."),
  quantity: 2
}
```

Пример:

```js
ingredients: [
  {
    type: "ingredient",
    ingredientId: ObjectId("..."),
    quantity: 2,
    quality: "normal"
  }
]
```

---

# 18. Качество ингредиентов

Качество лучше хранить отдельным значением, а не частью названия.

Плохо:

```text
фрукт (фиолетовое качество)
```

Хорошо:

```js
{
  category: "fruit",
  quality: "purple"
}
```

Возможные значения:

```text
normal
green
blue
purple
```

При необходимости список можно расширить.

---

# 19. Эффекты

Для небольшой базы эффект можно хранить непосредственно внутри рецепта:

```js
effect: {
  name: "Быстрое рыхление",
  level: 2
}
```

Это проще всего.

Если эффектов станет много и потребуется отдельное управление ими, можно создать коллекцию:

```text
effects
```

Пример:

```js
{
  _id: ObjectId,
  name: "Быстрое рыхление",
  levels: [1, 2]
}
```

# 23. Основная схема данных

```text
ingredients
     ↑
     │
recipes
     │
     │
recipe_submissions

flowers
     │
     ↓

```

Рецепты и цветы живут в одном проекте, но логически независимы.

---

# 24. Почему ингредиенты нужно хранить отдельно

Это позволяет:

- не дублировать названия;
- исправить название ингредиента один раз;
- фильтровать рецепты;
- строить поиск;
- определять категории;
- использовать один ингредиент в сотнях рецептов;
- корректно работать с требованиями вроде «любой фрукт»;
- позже добавить иконки ингредиентов.

---

# 25. Почему скрещивания лучше хранить отдельно

Это позволяет:

- быстро строить таблицу для конкретного цветка;
- показывать все способы получения нужного цвета;
- искать по результату;
- фильтровать по редкости;
- не смешивать логику рецептов и цветов в одной коллекции;
- в будущем добавить калькулятор скрещивания.

---

# 26. Итоговая минимальная структура

Для первой версии сайта достаточно:

```text
recipes
ingredients
recipe_submissions
flowers
flower_crosses
```

Без:

```text
users
favorites
ratings
popularity
recipe_images
```

Это оставляет архитектуру простой и при этом позволяет позже без серьёзной переделки добавить новые функции.
